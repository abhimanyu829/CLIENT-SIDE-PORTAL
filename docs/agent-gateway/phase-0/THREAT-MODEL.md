# Phase 0 — Future Agent Threat Model

No mitigations are implemented in this phase. Each threat is documented with the specific existing-system fact that makes it concrete (not generic), plus the required future control.

| Threat | Why it's concrete here (existing-system fact) | Required future control |
|---|---|---|
| Stolen agent credential | No `AgentConnection` exists yet, but the pattern is: whatever replaces it must not repeat the mistake found in `SubadminAccount` where `accessTokenHash` exists but the actual session token model (`SubadminSession`) is the real revocation lever — a stolen long-lived credential without a short-lived, revocable session on top of it is dangerous | Short-lived tokens + a revocable session/connection-status layer (`AgentConnection.status`), exactly as spec'd |
| Compromised AI host | An external Claude/Hermes/etc. host is outside this codebase's trust boundary entirely | Per-connection capability scoping (`AgentCapability.enabled`) so a compromised host can only exercise what was explicitly granted, never "whatever the underlying service function can technically do" |
| Prompt injection (direct) | This app has zero LLM-driven admin actions today — no existing attack surface, but `lib/openai.ts`/AI-agent invoke routes exist for other purposes and show the pattern of passing user content to a model | Tool inputs must be schema-validated (zod-equivalent) before reaching any business-service call — never string-interpolated into a privileged action |
| Indirect prompt injection (malicious external content) | `app/api/ai/recommendations/route.ts` and product-description fields are exactly the kind of content an agent might read and then act on | Any tool whose *output* includes untrusted content (product descriptions, ticket messages, lead notes) must be treated as data, not instructions, downstream — this is a host-side (AI platform) concern but the gateway should never itself execute a tool call based on parsing the *content* of a previous tool's result |
| Malicious/malformed tool arguments | Confirmed gap: `app/api/admin/service-discovery/[id]/route.ts` accepts an unvalidated `data` object and passes it straight to `Prisma.update()` — this exact pattern, if ever wrapped as a tool without a field allowlist, is a direct path to arbitrary-field mutation | Every tool's `inputSchema` must be a strict allowlist, and the Backend Adapter must re-validate against it — never trust the MCP client's own schema advertisement |
| Excessive permissions granted | `SubadminAccount`/`SubadminPermission` shows the human precedent: a permission-matrix that must be explicitly granted per resource/action, defaulting to nothing | `AgentCapability.enabled` must default `false`; the admin promotes, the AI never self-grants (mirrors the existing "admin promotes autonomy mode" principle) |
| Privilege escalation via agent | Confirmed CRITICAL-tier capability: `admin.changeRole`/`subadmin.createAccount` — these must be permanently excluded from ever becoming a generic tool, full stop, matching the architecture spec's hard exclusions | Architectural exclusion, not a policy toggle — these tools should not exist in the registry at all |
| Cross-team/cross-resource access | Ownership checks today are inconsistent: some routes have a working admin bypass (`subscription.userId===session.user.id \|\| isAdmin`), others have dead-code bypasses (tickets/projects — stale role strings), others have zero bypass (refund request) | `AgentIdentity.ownerId`/`teamId` must be checked against resource ownership using the **same** predicate the human path uses — not a new, potentially looser one |
| Unauthorized publication / runaway mutations | `products.updateStatus`/`republishProduct` are HIGH_RISK and currently have zero rate limit beyond the general 2000/15min tier — an agent with `products.publish` capability could publish/unpublish rapidly | Per-tool rate limits *tighter* than the general API tier (architecture spec's "10 publish_product/hour" example is directly appropriate here) |
| Repeated/duplicate mutation (replay or retry) | Confirmed concrete gaps: stock decrement (no idempotency key), refund gateway call (no idempotency key), subscription upgrade (Stripe call before DB write, no compensating rollback) | Gateway-level `idempotencyKey`+`requestHash`, enforced *in addition to* fixing (or working around) the underlying gaps — the gateway cannot assume the business layer is idempotent |
| Budget exhaustion | No budget/spend-tracking concept exists anywhere in the current codebase for anything other than `AIUsageLog`/`ai-quota-service.ts` (token quotas for the existing AI features, unrelated to a future agent's spend) | `AgentPolicy.maxDailySpend`/`maxSingleActionSpend` must be net-new — nothing to inherit |
| Rate-limit abuse | Current rate limiting is keyed by user/IP, not by `connectionId` — an agent sharing a service account's IP/identity would inherit that identity's quota, not have its own | Per-connection rate limiting as spec'd; cannot reuse the current `proxy.ts` limiter keys as-is |
| Sensitive-data exfiltration | Confirmed concrete targets: `PurchasedService.config` (customer credentials), `Product.deliveryConfig`, any `decrypt()` call result — see DATA-SENSITIVITY-MATRIX.md | Tool `outputSchema`s must never include these fields; redaction at the adapter boundary, not just policy documentation |
| Tool misuse (technically authorized, contextually wrong) | E.g. an agent with `products.delete` capability legitimately granted, but invoked against the wrong product due to a reasoning error | `ApprovalRequest` + `diffSummary`/`estimatedImpact` for any HIGH_RISK+ tool — human sees exactly what will change before it executes, per the architecture spec's approval flow |
| Confused-deputy attack | An agent authenticated as itself, tricked (by injected content or a buggy prompt) into requesting an action "on behalf of" a different resource/owner than intended | Resource-scope validation must happen against the **authenticated connection's** owner/team, never against a resource ID supplied in the tool call alone — exactly the pattern already correctly used by `entitlement.userId !== userId` checks (no admin-bypass, strict ownership) in this codebase |
| Replay attack (network-level) | Already covered under "repeated/duplicate mutation" but distinct in mechanism: a captured, still-valid signed request replayed by a network attacker rather than the legitimate agent retrying | Nonce (single-use, TTL-bound, stored in Redis per the spec's `<connectionId>:<nonce>` pattern) — genuinely net-new, no first-party precedent exists in this codebase (see SECURITY-BASELINE.md) |
| Compromised connector/MCP server itself | Not applicable to Phase 0 (gateway doesn't exist yet) — flagged for Phase 1 design: the gateway's own compromise is the single highest-blast-radius threat in the whole system, since it sits between every external AI and the real backend | Defense-in-depth: the gateway must never hold standing DB credentials beyond what a normal application server has; it must call through the same auth-checked service layer, so even a fully compromised gateway process cannot do more than a compromised *legitimate* admin session already could |

## Threats explicitly out of scope for this system today (confirmed absent, not overlooked)

- Arbitrary SQL/shell execution as an agent tool — confirmed no such primitive exists to even accidentally wrap (see DANGEROUS-PRIMITIVE-AUDIT.md).
- Payment-provider or authentication configuration as an agent tool — no such admin capability exists in the current codebase at all (payment/auth config is env-var/dashboard-level, not an in-app admin action).
